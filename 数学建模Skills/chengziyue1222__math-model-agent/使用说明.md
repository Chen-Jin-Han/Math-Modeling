# Math Model Agent：2026 国赛使用说明

> 适用赛事：全国大学生数学建模竞赛（CUMCM）
>
> 版本：2026.09.10
>
> 默认工作流：`competition`
>
> 使用原则：官方规则优先、核心建模由参赛队主导、全过程可复核、不得虚构证据

本说明面向正在参加国赛的团队，重点回答四件事：如何启动 Skill、如何推进建模、如何形成论文，以及如何按 2026 年规则完成提交。仓库的工程检查可以比官方要求更严格，但不能把本地偏好说成全国统一规定。

当前仓库包含 25 个模块文件和 149 个公开导出，并提供 8 个标准 Codex Skills；具体能力以实际代码、测试和校验脚本为准。

## 1. 今晚开赛后怎么开始

### 1.1 准备比赛目录

把官方题面和附件原样保存到同一个项目目录。不要覆盖、改名或直接编辑原始数据，建议结构如下：

```text
competition-project/
├── problem/                 # 官方题面及附件，只读保存
├── data/
│   ├── raw/                 # 原始数据，只读保存
│   └── processed/           # 清洗、转换后的数据
├── docs/                    # 题意、数据字典、任务拆解
├── src/                     # 自编程序
├── results/                 # 数值结果与验证结果
├── figures/                 # 正式图表及源数据
├── paper/                   # Markdown、TeX、PDF 或 DOCX
├── support/                 # 支撑材料候选文件
└── reports/                 # 检查与复现报告
```

身份信息词典 `.cumcm-identities.json` 只放在项目根目录，供本地匿名检查使用，不得进入论文或支撑材料。

### 1.2 第一条指令

在 Codex 新任务中附上题面和数据，然后发送：

```text
$run-modeling-project

按 competition 模式完成本次 CUMCM 项目。先完整读取官方题面和附件，保存原始文件，不虚构数据、参数、文献、代码运行或验证结果。

第一阶段只输出：
1. 每个子问题的目标、输入、输出、变量、单位和约束；
2. 子问题之间的依赖关系；
3. 数据质量、样本覆盖、缺失信息与外部资料需求；
4. 每题的候选模型、简单基线、淘汰条件和验证方案；
5. 当前风险、待确认事项和下一步工作顺序。

下游证据若推翻前面的选择，必须回退改模并同步更新结果、图表和论文。未经运行和核验的内容不得写成已完成事实。
```

`$run-modeling-project` 是默认总入口，会按需要调用其他建模 Skill。无需在第一条消息里堆叠全部 Skill。

### 1.3 分阶段调用

需要单独处理某一步时，在消息开头显式写 Skill 名称：

```text
$analyze-model-data 检查这些数据的字段、单位、缺失、异常、依赖结构和泄漏风险。
```

```text
$select-model 比较每个子问题的候选路线，给出主模型、简单基线、淘汰条件和验证方案。
```

```text
$solve-model 根据已经确认的路线建立方程、运行求解，并完成约束、基线、敏感性和稳健性检查。
```

```text
$make-model-figures 仅根据已保存的结果生成论文图表，每张图说明主张、数据源、单位和解释。
```

```text
$research-model-literature 查找参数、方法和外部事实的原始来源，核对 DOI、网页或官方数据入口。
```

```text
$write-model-paper 根据已验证结果生成 CUMCM 论文，不得补写不存在的数字、实验或引用。
```

```text
$review-model-paper 对论文、匿名信息、AI 声明、支撑材料和复现性做最终提交检查。
```

## 2. 2026 年国赛官方红线

本节是全国组委会规则的工作化摘要。若赛区通知或信息管理系统给出更具体要求，应同时遵守；发生冲突时，以更新、更具体的官方通知为准。

### 2.1 竞赛纪律

- 竞赛期间必须由本队独立完成赛题。
- 指导教师在竞赛期间不得解释题目、给出选题或解题建议、提供资料、修改论文或提出修改建议。
- 不得与队外任何人讨论赛题，也不得在贴吧、QQ 群、微信群、直播间、知乎、小红书、CSDN、GitHub 等交流平台浏览、发布或讨论与赛题相关的内容。
- 可以使用 AI 工具辅助，但核心建模与分析必须由参赛队主导；参赛队对原创性、真实性和准确性承担全部责任。
- 引用论文、网页、公开数据或他人成果时，必须在正文标注并列入参考文献，不得大篇幅照抄。

允许的资料检索应服务于独立建模，例如查阅原始论文、官方统计数据、标准或软件文档。不要搜索或浏览本届赛题讨论、答案、他队思路和代做内容。

### 2.2 论文版式与页数

| 项目 | 2026 全国统一要求 |
|---|---|
| 纸张 | 白色 A4，单面或双面均可 |
| 页边距 | 上下左右均至少 2.5 cm |
| 纸质版第 1 页 | 承诺书 |
| 纸质版第 2 页 | 编号专用页 |
| 纸质版第 3 页 | 摘要专用页 |
| 电子版第 1 页 | 摘要专用页；不放承诺书和编号页 |
| 摘要 | 含题目和关键词，原则上不超过一页，无需英文翻译 |
| 页码 | 从摘要页开始，以阿拉伯数字 `1` 连续编号，位于页脚中部 |
| 目录 | 不要目录 |
| 正文 | 摘要之后开始，正文内容不超过 30 页 |
| 附录 | 正文之后，页数不限 |

摘要页不计入正文 30 页上限。因此，电子版正文恰好 30 页时，附录可以从电子版第 32 页开始。

全国统一规范没有规定字号、字体、行距和颜色。仓库模板中的宋体、黑体、行距和标题层级属于本地可覆盖的排版默认值，不是全国统一硬性要求。赛区另有规定时按赛区规定执行。

### 2.3 附录、论文文件与支撑材料

- 附录应列出支撑材料的完整文件清单。
- 附录应包含本队编写的全部完整、可运行源程序，包括 Excel、SPSS 等软件的交互命令；确实没有使用程序时，应在附录明确写明。
- 电子论文必须是一个单独的 PDF 或 Word 文件，推荐 PDF，不得压缩，文件不超过 20 MB。
- 电子论文应与纸质论文内容和格式一致，并包含附录，但不包含承诺书和编号专用页。
- 支撑材料使用 ZIP 或 RAR，单个压缩文件不超过 20 MB。
- 支撑材料至少包括必要的可运行源程序、自主查阅的数据资料、较大篇幅中间结果或图表；赛题直接提供的原始数据不必重复装入。
- 所有论文、附录、支撑文件、文件名和元数据中都不得出现队员、学校、赛区、学号、用户名或能反推出身份的信息。
- 若确实没有任何支撑材料，官方规则允许不提交支撑压缩包，但必须在附录说明“本论文没有支撑材料”。本仓库的正式预检默认更严格，会要求支撑包和清单；比赛中使用 AI 时必须提交 AI 详情 PDF，因此通常一定存在支撑材料。

### 2.4 AI 工具使用规定

自 2026 年 9 月 1 日起，论文必须在参考文献之前设置“AI工具使用声明”。二选一如实填写：

未使用 AI：

```text
本参赛队在竞赛过程中未使用任何AI工具。
```

使用 AI：

```text
本参赛队在竞赛过程中使用了AI工具，主要用于【按实际填写用途】，详细使用情况见支撑材料。
```

只要在竞赛期间使用 Codex、大语言模型、生成式 AI、代码辅助工具或 AI 智能体，就应选择“使用 AI”。不得把实际参与建模、代码或分析的 AI 只申报为“语言润色”。

使用 AI 时，支撑材料必须包含一个可正常打开的 PDF，文件名必须准确为：

```text
AI工具使用详情.pdf
```

详情至少记录：

1. AI 工具名称、版本或型号；
2. 具体使用目的和环节；
3. 主要提示方式与使用过程，可附代表性交互；
4. 输出的采纳情况、人工修改和人工核验；纯语言润色可以不逐项写核验。

建议从第一轮 AI 对话开始维护 `support/ai-usage-log.md`，每次记录时间、工具/模型、任务、采用内容、人工修改和核验方法，赛末再整理为 PDF。可使用：

```text
skills/write-model-paper/assets/ai-tool-usage-details-template.md
```

不得通过所谓“AI 文风检测”倒推使用情况；声明应与实际交互、生成文件、版本记录、人工修改和复核证据一致。隐瞒、虚假声明或直接提交未经必要人工核验的 AI 核心成果，可能被取消评奖资格。

## 3. 八个标准 Skill

| Skill | 何时使用 | 关键产物 |
|---|---|---|
| `$run-modeling-project` | 完整比赛总控、阶段切换和交接 | 任务拆解、阶段状态、下一步行动 |
| `$analyze-model-data` | 数据表、CSV、Excel、时间序列或面板数据 | 数据字典、质量报告、清洗记录、泄漏检查 |
| `$research-model-literature` | 方法依据、参数、外部数据和引用 | 已核验来源、用途说明、BibTeX |
| `$select-model` | 选择或修正模型路线 | 候选比较、主模型、基线、反证与风险 |
| `$solve-model` | 建立方程、实现算法、求解与验证 | 模型说明、结果、基线和验证证据 |
| `$make-model-figures` | 生成论文图、诊断图和决策图 | 图形、源数据、图形说明和审计信息 |
| `$write-model-paper` | 从已验证材料形成论文 | Markdown/TeX/PDF 或 DOCX、附录和声明 |
| `$review-model-paper` | 定稿前查错与提交预检 | 分级问题、修订建议、提交就绪结论 |

Skill 可以通过自然语言自动触发，但比赛中建议显式使用 `$skill-name`，避免阶段意图不清。多个 Skill 可以同时写在一条消息中，例如：

```text
$analyze-model-data $select-model
先完成数据证据检查，再比较可行模型；暂时不要写论文。
```

## 4. 证据驱动的比赛工作流

### 4.1 题意与任务拆解

对每个子问题写一张任务卡：

- 输入对象、字段、时间范围、空间范围和单位；
- 决策变量或待估参数；
- 目标、硬约束、软偏好和评价指标；
- 最终需要提交的数值、图表、方案、排序或解释；
- 与其他子问题共享的数据、状态、约束和求解内核；
- 尚不清楚的条件，以及什么证据会改变路线。

不要按 A/B/C/D 题号机械套模型，也不要为了形式强行建立“统一模型”。只有多个子问题确实共享状态、约束、数据或求解结构时，才建立共同模型层。

### 4.2 数据分析

必须先保存原始数据，再进行：

1. 字段、类型、单位、来源和允许范围检查；
2. 缺失、重复、异常、零值和采样覆盖检查；
3. 目标泄漏、时间泄漏和实体泄漏检查；
4. 训练、验证、最终留出划分；
5. 只在训练数据上拟合插补、缩放、编码和特征选择；
6. 保存每项清洗操作及理由。

不得因为异常值破坏结论就删除它。插值、模拟、专家假设和外部补充数据必须标明来源，不能伪装成原始观测。

时间预测使用时间顺序留出；分组或面板数据按实体、地点或事件成组划分。随机划分不能作为未来外推的唯一证据。

### 4.3 模型选择

每个关键子问题至少建立一个可解释的简单基线，再决定是否需要复杂模型。候选模型按以下条件比较：

- 与题目机制是否匹配；
- 假设能否解释和验证；
- 参数能否由现有数据识别；
- 数据量、时间结构和样本覆盖是否足够；
- 输出是否直接回答原题；
- 是否有独立验证或反证方法；
- 在比赛剩余时间内是否能实现、复现和解释。

不要求固定候选数量、模型数量或创新点数量。关键假设不成立时，总分再高或算法再新也应淘汰。

### 4.4 建模、求解与验证

先写清变量、单位、目标、约束、初边值、参数来源和适用范围，再选择求解器。

每个关键结论应选择适合它的验证：

| 结论类型 | 优先验证 |
|---|---|
| 预测 | 朴素基线、时间/分组留出、校准、误差分布、外推风险 |
| 优化 | 可行性、约束余量、上下界、替代求解器、多起点 |
| 仿真 | 多随机种子、置信区间、守恒、极端情形 |
| 机理模型 | 量纲、边界、极限情形、守恒、参数可识别性 |
| 综合评价/排序 | 指标方向、归一化、权重来源、删指标与权重敏感性 |
| 网络或路径 | 图定义、方向、权重含义、可行路径和独立重算 |

参数敏感性与数值收敛是两件事，必须分开。最终测试集或外推段应在指标和决策规则确定后使用，不得反复查看并调参直到“通过”。验证失败时，保留失败结果并返回数据或模型选择阶段。

不存在跨题目通用的“MAPE 小于某值即优秀”标准。合格阈值必须来自任务损失、领域容差、基线、测量误差或决策后果。

### 4.5 图表

每张正式图都应回答一个问题，而不是填版面。图表数量由证据链决定，不设最低数量。

图中应根据需要标明：

- 变量名与单位；
- 样本范围与情景；
- 基线、阈值、可行域或不确定性；
- 颜色、线型和图例的含义；
- 源数据及生成程序。

不默认使用饼图、雷达图、双轴图、彩虹色图或装饰性三维效果。修改已有图时不得悄悄改变数据、筛选口径、尺度或结论方向。

### 4.6 结果解释

正文中的重要结果按以下顺序解释：

1. **结果**：数值、区间、排序或方案；
2. **模式**：趋势、阈值、拐点、差异或稳定区；
3. **机制**：模型结构为什么产生这一模式；
4. **证据**：基线、误差、约束、敏感性或独立复核；
5. **含义**：如何回答原题，以及适用边界和局限。

内部的 PASS/FAIL、哈希、JSON 和运行状态用于后台检查，不应充当论文论证。

## 5. 论文写作

### 5.1 推荐结构

```text
题目
摘要
关键词
问题重述
问题分析
模型假设
符号说明
各子问题：模型建立 → 求解 → 结果 → 验证与解释
模型检验、敏感性或稳健性分析
模型评价、局限与推广
AI工具使用声明
参考文献
附录
```

这只是推荐结构。若题目需要不同组织方式，可以调整；不得添加目录。

### 5.2 摘要

摘要必须在一页内完成闭环：

- 问题本质和总体路线；
- 每个子问题采用的方法；
- 最重要的可核对结果；
- 必要的验证或稳健性证据；
- 适用范围或关键局限；
- 关键词。

官方没有规定统一摘要字数。不要为了满足某个字数区间删除关键结果，也不要堆砌模型名称。

### 5.3 公式、表格与图

- 公式前说明为什么需要该关系，公式后定义变量、单位、求解方式和适用条件。
- 表题置于表上方；长表保留代表性结果，完整数据放入支撑材料。
- 图在正文中先被引出，图后解释模式、机制和局限。
- 关键数字应从保存的结果文件生成，禁止手工抄写后失去一致性。
- 公式、图、表和参考文献都没有官方固定数量要求。

### 5.4 引用

引用只使用实际查阅且与论证有关的来源。优先原始论文、官方数据、标准和权威文档。每个引用应能回答“支持哪条陈述、证据在何处”。不得引用不存在的 DOI、无法访问的网页或只从二手摘要猜测的内容。

### 5.5 CUMCM 模板与预览

仓库的 CUMCM TeX 起始模板为：

```text
skills/write-model-paper/assets/cume-template.tex
```

它是仓库排版默认值，不替代当届官方和赛区通知。生成模板预览：

```powershell
python skills\write-model-paper\scripts\render_template_preview.py `
  --output-dir output\pdf
```

检查 TeX 和最终 PDF：

```powershell
python skills\write-model-paper\scripts\validate_cumcm_layout.py `
  --project-root path\to\project `
  --tex path\to\project\paper\main.tex `
  --pdf path\to\project\paper\main.pdf `
  --report path\to\project\reports\layout-validation.json
```

必须实际渲染并逐页查看最终 PDF，不能只看 TeX 源文件或使用浏览器截图代替。

## 6. 支撑材料与复现

推荐支撑包结构：

```text
support-package/
├── README.md                    # 环境、安装和复现命令
├── requirements.txt             # 第三方依赖及版本
├── src/                         # 完整自编源程序
├── data/                        # 自主查阅或处理后数据
├── config/                      # 参数与配置
├── results/                     # 必要中间结果
├── figures/                     # 大篇幅图表或绘图源数据
├── AI工具使用详情.pdf           # 使用 AI 时必需
└── support-manifest.json        # 文件清单与复现命令
```

支撑材料必须满足：

- 清单与压缩包中的文件逐项一致；
- 所有路径使用项目相对路径；
- 在新建的干净目录解压后，可以按 README 命令运行；
- 不包含虚拟环境、第三方库源码、大型无关缓存或身份词典；
- 论文结果与程序实际输出一致；
- `AI工具使用详情.pdf` 能打开、可提取文字并覆盖官方要求的四类信息。

第三方软件只记录名称、版本和安装方式，不复制其完整源码或二进制文件。

## 7. 最终审查

### 7.1 用 Skill 审查

```text
$review-model-paper

按 CUMCM 2026 competition 标准审查当前项目。先检查官方合规，再检查模型与证据质量。重点核对正文 30 页口径、摘要首页、无目录、连续页码、匿名信息、AI 声明位置、AI 详情 PDF、附录文件清单、完整源程序、论文与支撑材料各 20 MB 限制，以及干净目录复现。按严重程度报告问题；任何阻塞项未解决时不得声称提交就绪。
```

### 7.2 本地预检

先从示例建立私密身份词典：

```powershell
Copy-Item config\cumcm-identities.example.json `

```

填写所有队员姓名、学校、赛区、学号、制作者电脑用户名和其他敏感词。该文件不得进入提交材料。

运行论文和支撑包预检：

```powershell
python skills\review-model-paper\scripts\submission_preflight.py `
  --project-root path\to\project `
  --pdf path\to\project\paper\main.pdf `
  --paper-source path\to\project\paper\main.tex `
  --support-archive path\to\project\delivery\support.zip `
  --support-manifest path\to\project\delivery\support-manifest.json `
  --report path\to\project\reports\submission-preflight.json
```

如果交付 Word，则将 `--pdf` 换成 `--docx`。本地工具的 PASS 只说明通过了当前检查，不代表一定获奖，也不能代替人工逐页核对和信息管理系统的最终要求。

### 7.3 提交前清单

#### 官方合规

- [ ] 使用官方当前题面和赛区通知，没有旧模板混用。
- [ ] 电子版第 1 页为摘要，摘要含题目和关键词且原则上不超过一页。
- [ ] 不含目录，页码从摘要的 1 开始并位于页脚中部。
- [ ] 正文不超过 30 页；摘要页未误计入正文，附录位于正文之后。
- [ ] A4 且四周页边距至少 2.5 cm。
- [ ] 论文为单个 PDF 或 Word 文件，大小不超过 20 MB。
- [ ] 支撑材料为单个 ZIP/RAR，大小不超过 20 MB。
- [ ] 附录列出支撑材料全部文件，并包含全部完整自编程序；无程序或无支撑材料时已按规定说明。
- [ ] 正文引用与参考文献一一对应。
- [ ] 论文、支撑材料、文件名和元数据均无身份信息。
- [ ] `AI工具使用声明` 位于参考文献之前，内容与实际使用一致。
- [ ] 使用 AI 时，支撑包包含准确命名且内容完整的 `AI工具使用详情.pdf`。

#### 模型与证据

- [ ] 每个子问题都有明确输入、输出、变量、单位、约束和可执行结果。
- [ ] 数据处理无训练/验证泄漏，所有补充数据和参数有来源。
- [ ] 复杂模型与简单基线在相同数据、约束和指标下比较。
- [ ] 关键结论有与任务匹配的验证，失败结果没有被隐藏。
- [ ] 图表和正文数字都可追溯到机器可读结果。
- [ ] 结论说明机制、证据、适用范围和局限。
- [ ] 支撑包能在干净目录复现主要结果。

#### 最终文件

- [ ] 打开最终文件，而不是中间版本或缓存副本。
- [ ] 逐页检查乱码、裁切、重叠、空白页、跨页表格和图片清晰度。
- [ ] 核对上传系统中的文件名、格式、大小和截止时间。
- [ ] 上传后重新下载并检查文件能否打开、页数和大小是否正确。

## 8. 常见问题

### 8.1 是否需要一次引用全部 Skill？

不需要。完整项目使用 `$run-modeling-project`；遇到明确阶段任务再单独调用对应 Skill。一次堆叠全部 Skill 容易让数据、模型和写作同时展开，反而难以核验。

### 8.2 Skill 给出的模型必须一直使用吗？

不是。模型选择是可审查的假设。下游数据、求解或验证推翻关键假设时，应记录原因并回到最早受影响的阶段，随后更新所有依赖结果。

### 8.3 图、公式和参考文献越多越好吗？

不是。官方没有固定数量门槛。只保留能解释模型、呈现结果或提供验证证据的内容。

### 8.4 是否可以让 AI 直接完成整篇论文？

AI 可以辅助，但核心建模与分析必须由参赛队主导，所有 AI 参与内容都要人工审查与核实。不得把未经核验的 AI 输出直接作为核心成果提交。

### 8.5 预检 PASS 是否等于可以获奖？

不等于。预检只降低格式、匿名、证据和复现错误风险。模型洞察、问题理解、数据质量和真正有效的创新仍决定论文质量。

### 8.6 为什么本地检查比官方要求更严格？

官方规定的是最低合规边界；仓库还要求清单一致、干净目录复现、来源追溯和 AI 详情内容检查，用来降低临近提交时出现缺文件、程序不可运行或声明不一致的风险。报告问题时应注明它属于“官方合规”还是“本地质量门禁”。
