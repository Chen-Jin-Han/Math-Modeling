# 组装空间 — 行为规则

## 触发方式

当用户说出以下任一内容时，你立即切换至组装空间模式：
- 「组装空间」
- 「组装论文」
- 「把部件拼成论文」
- 「部件都改完了，合成一篇」

## 背景

多人协作时，论文按题拆成部件（Q1/Q2/Q3/公有），每人负责一个部件文件，改完后交回。组装空间的职责：**把部件按模板结构拼成一篇完整论文并正确编译出 PDF，不改变任何正文内容**（文字/数字/公式/图片一律冻结）。

## 核心原则

**内容冻结。** 组装过程只允许修改结构命令；任何对正文内容（文字、数字、公式、图片）的修改都必须上报用户决定，绝不静默修改。

**进入组装空间后先向用户说明将做什么（交回核对 + 拼接 + 编译，不动任何正文内容），确认后再动手。** 若用户直接手改了组装产物（如 main_combined.tex），以最新版为准：先对改动做结构 diff，正文改动直接接受，结构改动走白名单，不因"内容冻结"阻塞用户自己的修改。

## 输入

- 部件文件：`part_q1.tex` … `part_qN.tex`（N = 题目数量）+ `part_common.tex`（命名约定见 `references/assembly/part-template.tex`）
- 主模板：`references/cumcm-template/cumcm2026_template.tex` + `cumcmthesis.cls`（**骨架背书**：章节顺序、preamble、三线表/公式/图表环境定义以此为准）
- **格式检查表：`references/checklists/contest-format.md`（格式背书：国赛/美赛格式要求——三线表、图下/表上、中文引号、公式编号、伪代码附录等，组装产物终检以此为准）**
- 图片文件（各部件引用的 figures）
- 总框架：`paper-framework.md`（多人模式由 Phase 4 生成，含章节结构 / 组装顺序 / label 命名约定 / 术语格式约定；**结构背书**）
- 分发文件夹（`part_q1_分发/` 等，含 README / 背景材料 / code_qN）**参与交回核对（步骤 0），不参与拼接**——拼接只接收部件文件、模板与图片
- 交回文件：`交回/part_q1_分发/` 等（队友改完原样发回、用户放入收件目录）

**组装三依据**：结构以 `paper-framework.md` 为准、格式以 `contest-format.md` 为准、骨架以 `cumcm2026_template.tex` 为准——三者任一缺失时先说明兜底方式再动手。

## 执行步骤

### 0. 交回核对（多人模式强制）

拼接之前，对每个交回文件夹执行：
1. **完整性核对**：README 文件清单（"改完交回"列）vs 实际交回文件——缺失/新增/改名逐项列出；**部件文件（part_qN.tex）缺失时先上报用户确认，不静默跳过**；交回文件保持分发时结构（队友整文件夹原样发回，收件目录 `交回/`）
2. **结构 diff 用脚本替代人工**：运行 `references/scripts/handback-check.py --dist <分发目录> --ret <交回目录>`——输出锚点注释缺失（H1）、文档级命令混入（H2）、label 变更与前缀越界（H3）、新增 \input（H4）。**不拦正文改动**（队友改正文是预期），只查结构
3. **问题分流**：结构问题在白名单（步骤 4）内 → 修复并记入 diff 报告；白名单外或涉及正文 → 上报用户决定

### 1. 组装清单先行（强制）
多人模式（存在 `paper-framework.md`）：**先读取框架文件**，按其章节结构与组装顺序生成「锚点 → 文件」映射；框架缺失 → 按模板结构兜底并上报用户。单人模式直接按模板章节顺序：

```
摘要（问题一→二→三句组）→ 问题重述（各题）→ 问题分析（各题）→
假设 → 符号说明 → 模型准备 → 问题一建模求解 → 问题二 → 问题三 →
模型测试与分析（灵敏度）→ 模型评价 → 参考文献 → 附录（各题代码）
```

每个锚点对应哪个部件文件的哪个片段。**先展示给用户确认，确认后才动手拼。**

### 2. 拼接（默认单文件输出）
- 创建论文目录，复制模板 + `.cls` + 图片
- **默认输出单文件 main.tex**（第三次模拟反馈：23 个 frag 片段太零散、用户习惯直接编译整文件）——模板 preamble + 各部件内容按组装顺序内联，每个部件内容前保留锚点注释行（`% ─── part_q1 开始 ───`）便于定位；`\input` 方式降为可选（用户明确要求时才用）
- **重跑组装会覆盖对 main.tex 的手改**——重新组装前先备份用户已改的 main.tex，并提示用户
- 部件文件**禁止**包含 `\documentclass` / `\begin{document}` / `\usepackage` / `\newenvironment`（只在 main.tex），违者视为违规需先移除并上报

### 3. 编译
- `latexmk -xelatex`（或 xelatex 两遍）
- 编译错误 → 分类处理（见下方白名单）

### 4. 结构修复白名单（只能改这些）
| 可修改 | 示例 | 禁止（必须上报） |
|--------|------|------------------|
| `\input` 位置/顺序 | 调整片段插入位置 | 修改正文文字、数字、公式 |
| label 重命名 | `\label{fig:xx}` 冲突时加前缀 `q1:` | 修改图片内容/尺寸语义 |
| 宏定义去重 | 多个部件重复 `\newcommand` → 移到 main.tex | 新增/删除正文段落 |
| 图片路径 | 大小写/扩展名/路径修正 | 改动表格数据 |
| 补 `\usepackage` | 缺宏包时在 main.tex 侧补 | 补充/改写摘要句子 |
| `\ref` 悬空修复 | 报告缺失 label，不静默补定义 | 修改参考文献列表 |

任何需要动正文才能过的编译错误 → 上报用户：「错误位置 + 原因 + 需要的修改」，由用户决定。

### 5. 交付
- **结构 diff 报告**：列出所有改动（加了哪些 \input、改了哪些 label、修了哪些编译错误），用户可逐条核对内容未被改动
- 校验清单：
  - [ ] 交回核对已完成（handback-check.py 输出 + 完整性核对，问题已分流处理）
  - [ ] 组装结构是否与 paper-framework.md 一致（章节顺序 / 部件归属 / label 前缀）
  - [ ] 编译 0 错误（允许 <8pt 的 overfull 警告）
  - [ ] `combinecheck.py` 通过：图/表/公式编号连续、引用率 100%（无悬空 \ref）、无重复 label
  - [ ] `citecheck.py` 通过：引用机制统一（无 \scite/\cite 混用）
  - [ ] 页数与各部件预览拼接后的预期一致（±2 页）
  - [ ] 无重复宏定义
  - [ ] 摘要顺序：问题一→二→三句组连贯
  - [ ] **格式背书：按 contest-format.md 核对组装产物**（三线表+tabcolsep、图下/表上、中文引号 “”、公式编号+引导句、符号表不参与编号、伪代码在附录）——不符合的列出并上报用户，不静默改

## 红线

- 绝不修改正文内容（文字/数字/公式/图片）
- 绝不静默修复——每个结构修改都进 diff 报告
- 部件文件缺失/含文档级命令 → 先上报再处理
- 组装完成 = PDF + diff 报告 + 校验清单三件套，缺一不算完成

## 与正常模式的切换

用户说「继续任务」「回到正常流程」时退出组装空间。
